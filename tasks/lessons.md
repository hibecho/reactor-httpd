# 项目经验

- 简化连接分发时，用明确的所有权标记消除嵌套异常处理；调用回调前标记交接，交接前的异常仍须释放 fd，交接后不得重复关闭。

- 仅用于初始化的端口由上层传入，Acceptor 不额外保存或提供查询接口；测试需要随机端口时在测试层查询监听 fd。

- 通用日志异常保护归属 Logger 的**唯一**入口。2026-09-19 用户改选「统一」：安全兜底并入 `HTTP_LOG_AT`，所有 `LOG_*` 一律不抛，不再保留单独的 `LOG_ERROR_SAFE`，业务模块也不得自己包 try/catch。配置接口（`Init`/`SetLevel` 等）仍然抛异常，那部分是契约，不要顺手一起改成不抛。保护必须覆盖单例获取、等级判断与参数求值，不能只包住后端输出。

- 兜底该写在哪一层，由「参数在哪求值」决定，不由「哪个类负责日志」决定。宏实参在**调用方**求值，把 try/catch 放进 `Logger::Log` 成员函数根本包不住它，所以「不抛」这个契约只能在宏里兑现。同理，判断第三方库是否已经替我们兜过底也必须读源码：spdlog 的 `SPDLOG_LOGGER_CATCH`（`logger.h:30-50`）确实接住了 `std::exception` 并转给 `err_handler_`，但它对非 std 异常是「记一条错误再重新抛出」，且参数求值、单例获取、`ShouldLog` 都在它的保护范围之外——正是这一点决定了我们的 catch 必须是 `...` 而不能收窄成 `std::exception`。

- 第三方库的「无异常」编译开关必须读实现再决定用不用，名字不可信。spdlog 的 `SPDLOG_NO_EXCEPTIONS` 看着正是「不抛异常」，实现却是 `common.h:97-104` 的 `printf` 一条 fatal 再 `std::abort()`——对服务器而言这是从「可能抛异常」退化成「直接终止进程」，比不开更糟。

- 用户要求小模块简洁易懂时，优先采用直接的显式流程，避免新增资源包装类；Acceptor 在复制回调失败和空回调时显式关闭 fd，调用开始后不再代为关闭。保留已验证的安全契约，用现有回归确认精简没有退化。

- 封装第三方日志模块时，公开等级使用模块自己的 enum class，不以第三方枚举别名代替抽象；转换留在模块内部，并同步所有配置示例。

- 用户当前以理解基础日志封装为主，明确要求降低复杂度后恢复纯同步实现；后续默认选择简单直接的实现，不重新引入异步队列或等待通知机制，除非用户再次明确要求。

- 调整编译参数时必须验证实际 Makefile 的完整编译和链接；单个 .cc 编译成功不能代表构建可用。发现缺失源码或循环包含，应一并解决后再给出可用方案。

- 断言"某对象析构后其登记已被清理"时，不能用指针身份比较来探测：栈上两个同类型对象先后析构与构造，很可能复用同一地址，陈旧表项会被误判成本人，断言静默失效。改用只看资源占用状态的探测（如对同一 fd 再次 AddEvent 是否被拒），与地址无关。

- 新增断言后必须做变异验证：把被断言的修复逐个改回去，确认测试确实失败。本轮就是靠变异验证发现了一条在 TestEpoller 有效、在 TestChannel 无效的断言。

- 头文件内联实现会向所有包含者传递依赖；把实现下沉到 .cc 时，必须为每个使用点补直接 include（Socket 拆分暴露了测试缺 <arpa/inet.h>/<cerrno>/Logger.hpp，Channel 拆分暴露了 Epoller.cc 缺 Logger.hpp、EventLoop.cc 缺 <unistd.h>）。同时要检查新增的链接依赖：Channel.cc 固定引用 EventLoop 的接口后，此前从未参与编译的 src/EventLoop.cc 必须进链接，否则失败。

- 用 eventfd 当作被监控的描述符时，读回调若只置标志而不 read 掉计数，该描述符在后续阶段仍持续可读，WaitEvent 就会多返回本不该就绪的对象。迁移这类测试必须保留原有的 drain 步骤；本次迁移 TestEpoller 时漏掉 drain，Modify 段因此失败。

- 提高编译标准会激活只在更高标准下启用的警告，必须全量重建验证，不能只看改动点。`-std=c++11` 提到 c++17 后，自定义非 sized `operator delete` 触发 `-Wsized-deallocation`；补 sized 版本时必须转调非 sized 版本，若写成 `::operator delete[](p, size)` 会调用自身而无限递归。

- 看门狗不能用裸 `alarm`：SIGALRM 的默认动作直接终止进程，make 只留下 "Alarm clock"，无法定位是哪条断言挂住。应安装自定义处理器，内部只做异步信号安全的 `write` + `_exit`，并在每个用例开头重设预算。变异验证中"就绪事件永不产生"和"Update 空体"两项正是靠看门狗或异常逃逸暴露的——永久阻塞也是一种有效的失败模式，前提是它可被观测到。

- Channel 的监听位没有 public setter，一旦 Channel 改为经 EventLoop 转发，针对 Epoller 的测试就必须引入 EventLoop 才能让 Channel 带上监听位；但 EventLoop 的 `_ep` 私有，纯端到端驱动会丢掉 active 向量级别的断言。混合驱动（EventLoop 只提供监听位、裸 Epoller 承担登记与等待）能在迁移中同时保住两者。

- 头文件内联实现加互相包含会直接让整仓编译不过，且报错位置极具误导性：`TimerQueue.hpp` 包含 `EventLoop.hpp` 而后者回指前者，症状却是「`task_t` 未声明」「`read` 未声明」「EventLoop 类型不完整」。排查手段是对每个公开头文件单独做一次 `-fsyntax-only` 包含，以及单独编译每个 .cc；只看 `make` 的第一条报错会一路追错方向。判定「头文件是否自包含」只能靠这种方式，`make` 能过不代表头文件可用。

- 头/源分离的忠实度用机械比对而不是逐行人工核对：把拆分前后的文件各自做「去首尾空白 + 去空行」归一后取行集合求差，剩余差异应当全部能用「声明行、类名限定符、刻意改名、刻意修复」四类解释。这次正是靠它确认没有函数体被漏搬。

- 变异验证中出现「编译失败」不等于「已被捕获」：把 `return timeout > capacity ? capacity : timeout;` 改成 `return timeout;` 会让 `capacity` 变成未使用参数，被 `-Werror=unused-parameter` 拦下。这种时候必须换一种语义等价且不引入新警告的变异（如补 `(void)capacity;` 后保留原意），否则验证结论是假的。

- 断言应写成「这一步必须成功」，不要依赖自己推测的具体失败路径。`~TimerWheel` 不摘除登记时，预期的捕获是身份比较失败，实际是：析构释放的 fd 号被复用，新 Channel 由 `make_unique` 分配到与旧对象相同的地址，身份比较反而通过，最终由内核 `EPOLL_CTL_MOD` 返回 ENOENT 兜住。功能上没问题，但事后写文档若照搬推测就会失真。

- 边界归一化只做在入口：把 timeout 归一后存进 `TimerTask`，刷新路径用 `task->GetTimeout()` 重算时天然一致。若在每处用到 timeout 的地方各自钳位，添加与刷新就会走出两套边界。

- 给用户的修法建议在写进方案前必须先验一遍它是否成立，光"看起来显然"不够。这次提出的「把 `TimerTask*` 捕获进 lambda 做身份比对」，在 map 存 `weak_ptr` 的前提下就是错的：清理挂在 `~TimerTask` 上，此刻 `weak_ptr::lock()` 必然返回空（强引用计数已为 0），拿不到可比较的裸指针。`weak_ptr` 没有 `operator==`（它比的是被指对象地址、需要先 `lock()`），要判断「是不是同一个对象」应该用 `owner_before` 双向比较控制块。

- 改一个「删索引」的时机前，先问它是不是唯一的正确时机。把清理从 `~TimerTask` 挪到 `Tick()` 表面上更好写（任务还活着，`lock()` 可用），实际会破坏刷新语义：刷新过的任务同时挂在旧槽与新槽上，旧槽到期就摘索引，此后到新槽到期之间的整段时间里它既不能刷新也不能取消、却照样触发。析构才是「最后一根强引用消失」的唯一时刻，凡是靠对象生命周期收尾的清理都只能挂在那里。

- 「同一个 key 被新记录接管」时，旧记录的清理必须按身份而不是按 key 删除。索引类容器（id -> 引用）用「析构时按 id 删除自己」的写法时，旧对象一旦被新对象顶替，它的析构就会删掉新对象刚写下的记录，表现为新对象从此不能被刷新或取消、但照旧触发——静默且难查。这类断言要专门构造「旧对象先析构、再操作新对象」的时序才能覆盖。

- Connection 错误报告统一使用项目 LOG_ERROR，不另行使用 fprintf；在统一报告函数内部隔离日志异常，保证日志失败不跳过连接清理。

- 面向学习的收发结果处理，优先分开负数错误、零返回和正数字节数；仅在失败分支读取 errno，避免用合并条件掩盖不同语义。

- 解释所有权与生命周期问题时，先核实实际的持有关系再下结论，不能凭「谁指向谁」的直觉。`Connection` 持有的是 `EventLoop*` 裸指针（Connection.hpp 明确注释「不拥有它」），所以定时回调里捕获 `shared_ptr<Connection>` 的后果是**对象析构被推迟到时间轮槽位到期**（`TimerCancel` 只置 `_canceled`，任务对象仍留在槽里，最长 60 个 tick），而不是我先前所说的「引用环」。这类解释一旦说错，后续所有推理都会跟着错。

- `SwitchProtocol` 会整体替换四个业务回调（含关闭回调）。为它写用例时，若在调用它之前注册关闭回调，计数会永远是 0——切换把回调换成了空函数。涉及该接口的用例必须先切换、后注册需要观测的回调。

- 判定「某分支没有被覆盖」要以变异验证为准，不能靠通读代码下结论。本次候选里就有两条：`EnableInactiveReleaseInLoop` 的 `_release_pending || _released` 守卫删掉后，`HandleError` 的同名守卫会兜住，关闭通知仍只有一次；`HandleWrite` 的 `sent == 0`、`HandleEvent` 的 `TimerRefresh` 等也缺少可观测差异。这类用例写出来只会给出「测过了」的错觉。

- 断言必须落在**能区分变异**的观测点上。"析构时是否兜底注销登记"就无法用"对端收到 EOF / fd 已关闭"来证明——那些是 `~Socket` 的功劳，删掉 `_channel->Remove()` 后它们照样成立。可靠做法是制造同 fd 号重新登记的探针：`dup2` 把已释放的号码重新变成有效描述符，再登记新 Channel，残留表项会让这次登记失败（身份不符抛 `logic_error`，或地址恰好复用时由内核 `EPOLL_CTL_MOD` 返回 ENOENT 兜住）。断言写成「这一步必须成功」，而不是断言某种具体异常。

- 做变异归因实验（确认某条用例是不是某变异的唯一捕获者）时，直接把用例调用从 `main` 里删掉会触发 `-Werror=unused-function`，表现为编译失败——与「变异已被捕获」的结论混在一起就是假阴性。应改成保留引用而不调用，如 `(void)&CaseName;`。

- 用 `O_PATH` 描述符可以稳定构造 `fcntl` 的部分失败：`F_GETFL` 正常返回，`F_SETFL` 返回 EBADF。这为「非阻塞设置失败」提供了一条不需要伪造陈旧 fd、也不需要为测试目标新增 `--wrap=fcntl` 的干净路径。前提断言要写进用例，避免内核行为变化后静默失效。

- 改一个函数的参数类型时，必须回头检查原有的边界校验在新类型下是否仍然成立。`EnableInactiveRelease` 的参数从 `int` 改成 `uint32_t` 时，函数体里的 `if (timeout <= 0) throw ...` 一字未动，看起来仍然在防负数，实际已退化成只判 0：负数在实参转换处早就回绕成 4294967295，再被时间轮静默钳位到容量上限。规则：签名与校验条件是一对，改一边就要重新推导一遍另一边的语义，不能因为「代码没动」就默认它还有效。

- 没有接入任何构建目标的源码等于「不会报错的代码」。`Acceptor.cc` 曾有先 `Create()` 再 `CreateServer()` 导致绑定与监听被整体跳过的缺陷，还带着两个被丢弃的返回值，但因为它不在 Makefile 的任何目标里，从未参与编译——单独用项目同款严格参数做 `-fsyntax-only` 也是通过的，连 `-Werror` 都不会触发。规则：新模块写完立刻接一个编译目标，哪怕还没有测试。

- 调用一个「内部会再创建一次资源」的函数之前，必须先读它的实现。`Socket::CreateServer` 的第一句就是 `if (!Create()) return false;`，而 `Create()` 在描述符已存在时返回 false，所以先手动 `Create()` 再调 `CreateServer()` 会让后者在第一行就失败并跳过绑定与监听。两个函数名看起来是「分步」与「一步到位」的关系，实际是互斥的。规则：判断两个 API 能否串联，看被调方的实现，不看名字。

- 测试一个「绑定线程」的模块前，先确认它的线程归属契约落在哪一步。`TcpServer` 的 `EventLoop` 在构造函数里记录线程 id，`Acceptor::SetAcceptCallback` 又会校验当前线程，所以构造与 `Start()` 必须同线程；而 `Start()` 阻塞在主循环上，客户端的驱动逻辑只能放到另一个线程。动手写用例前没确认这一点，会先写出一版「在别的线程里 Start」的测试，然后在 `std::logic_error` 上白跑一轮。

- 析构函数里调用「会抛异常的注销接口」时，必须区分对象到底登记过没有。`Acceptor` 构造时只创建监听 Channel 不登记（登记在 `StartAccepting()`），而 `~Acceptor` 无条件 `Remove()`，于是「构造过但从未启动」的对象一析构就抛 `logic_error` 并 `terminate`。规则：析构路径上的清理动作，其前置状态要么由对象自己记录，要么接口本身对「本就没登记」幂等——`Connection` 用 `_registered` 记录，`Acceptor` 没记，差别就在这里。

- 断言「某操作被拒绝」时，若只捕获异常的基类，会接受「拒绝了，但拒绝得太晚」的实现。`std::system_error` 派生自 `std::runtime_error`，于是 `catch (const std::runtime_error &)` 同时接住了「在创建套接字处拒绝」和「带着无效描述符继续走到 epoll 登记才失败」两种情况，变异验证里这条用例因此假通过。修法是单独 `catch` 子类并把它判为失败。规则：断言异常类型等于断言语义，必须排除掉语义不同的子类。

- 把「一次调用 = 一轮」重新变成可独立调用的原语（`LoopOnce()`），比让每个测试自己造外层 `while` 更好。`Loop()` 改成持续循环后，六个测试目标挂在 `epoll_wait` 上，看起来是「测试写法过时」；真正干净的做法是把循环体抽成不循环的 `LoopOnce()`，`Loop()` 退化为 `while (!_quit) LoopOnce();`，测试改调单轮原语。规则：当循环语义变化时，先问「一轮」能不能是一个独立的、可被外部调用的操作，而不是急着改调用方。

- 一批测试长期挂在同一个位置时，它们后面的断言从未执行过，**不要把它们当作已验证**。`TestAcceptor.cc` 的 18 个用例全部按「构造即登记监听」写，而实现早已把登记挪到 `StartAccepting()`，头文件注释又是旧口径——三者不一致，但因为在改动前所有用例都卡在第一个 `Step()`，这个矛盾被完整地掩盖了。改完单轮驱动后，第一件事就是逐个跑一遍，而不是默认「原来就是绿的」。规则：解除挂死之后必须重新评估这批用例的断言是否还成立，这也是修 Loop 时必须连带处理的隐藏工作量。

- 变异验证结束后必须把源码还原并复查，残留的变异会伪装成「既有红项」。`TestBasic.cc:226` 留着上一轮的 `// MUTATION 4：对端关闭不回收`，导致 `check-integration` 从 2026-09-17 起一直红，而且被后来的几轮记成「与本轮改动无关的既有问题」，一路沿用。事后看，注释里明明写着 `MUTATION`，只要有人读一眼就能定性。规则：变异验证的副本要么放 `/tmp` 并在结束时删除，要么在还原后 `grep MUTATION` 复查；看到 `MUTATION` 字样的注释，先按「未还原」处理。

- 文档注释、实现、测试三者不一致时，先认定哪一个是「当前设计意图」再动手，不要默认注释或测试就是契约。`Acceptor` 的契约有三种可能的口径：注释说构造即登记、实现说 `StartAccepting()` 才登记、测试从不调用 `StartAccepting()`。判定依据不是谁的措辞更权威，而是**现有调用方怎么用**——`TcpServer::Start()` 先设 accept 回调再 `StartAccepting()`，说明「延迟登记」是刻意设计，于是改测试与注释，而不是改实现。
