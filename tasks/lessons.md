# 项目经验

- 简化连接分发时，用明确的所有权标记消除嵌套异常处理；调用回调前标记交接，交接前的异常仍须释放 fd，交接后不得重复关闭。

- 仅用于初始化的端口由上层传入，Acceptor 不额外保存或提供查询接口；测试需要随机端口时在测试层查询监听 fd。

- 通用日志异常保护归属 Logger 的**唯一**入口。2026-09-19 用户改选「统一」：安全兜底并入 `HTTP_LOG_AT`，所有 `LOG_*` 一律不抛，不再保留单独的 `LOG_ERROR_SAFE`，业务模块也不得自己包 try/catch。配置接口（`Init`/`SetLevel` 等）仍然抛异常，那部分是契约，不要顺手一起改成不抛。保护必须覆盖单例获取、等级判断与参数求值，不能只包住后端输出。

- 兜底该写在哪一层，由「参数在哪求值」决定，不由「哪个类负责日志」决定。宏实参在**调用方**求值，把 try/catch 放进 `Logger::Log` 成员函数根本包不住它，所以「不抛」这个契约只能在宏里兑现。同理，判断第三方库是否已经替我们兜过底也必须读源码：spdlog 的 `SPDLOG_LOGGER_CATCH`（`logger.h:30-50`）确实接住了 `std::exception` 并转给 `err_handler_`，但它对非 std 异常是「记一条错误再重新抛出」，且参数求值、单例获取、`ShouldLog` 都在它的保护范围之外——正是这一点决定了我们的 catch 必须是 `...` 而不能收窄成 `std::exception`。

- 第三方库的「无异常」编译开关必须读实现再决定用不用，名字不可信。spdlog 的 `SPDLOG_NO_EXCEPTIONS` 看着正是「不抛异常」，实现却是 `common.h:97-104` 的 `printf` 一条 fatal 再 `std::abort()`——对服务器而言这是从「可能抛异常」退化成「直接终止进程」，比不开更糟。

- 用户要求小模块简洁易懂时，优先采用直接的显式流程，避免新增资源包装类；Acceptor 在复制回调失败和空回调时显式关闭 fd，调用开始后不再代为关闭。保留已验证的安全契约，用现有回归确认精简没有退化。

- 封装第三方日志模块时，公开等级使用模块自己的 enum class，不以第三方枚举别名代替抽象；转换留在模块内部，并同步所有配置示例。

- 用户当前以理解基础日志封装为主，明确要求降低复杂度后恢复纯同步实现；后续默认选择简单直接的实现，不重新引入异步队列或等待通知机制，除非用户再次明确要求。

- 调整编译参数时必须验证实际 Makefile 的完整编译和链接；单个 .cc 编译成功不能代表构建可用。发现缺失源码或循环包含，应一并解决后再给出可用方案。

- 断言"某对象析构后其登记已被清理"时，不能用指针身份比较来探测：栈上两个同类型对象先后析构与构造，很可能复用同一地址，陈旧表项会被误判成本人，断言静默失效。改用只看资源占用状态的探测（如对同一 fd 再次 AddEvent 是否被拒），与地址无关。

- 新增断言后必须做变异验证：把被断言的修复逐个改回去，确认测试确实失败。本轮就是靠变异验证发现了一条在 TestEpoller 有效、在 TestChannel 无效的断言。

- 头文件内联实现会向所有包含者传递依赖；把实现下沉到 .cc 时，必须为每个使用点补直接 include（Socket 拆分暴露了测试缺 <arpa/inet.h>/<cerrno>/Logger.hpp，Channel 拆分暴露了 Epoller.cc 缺 Logger.hpp、EventLoop.cc 缺 <unistd.h>）。同时要检查新增的链接依赖：Channel.cc 固定引用 EventLoop 的接口后，此前从未参与编译的 src/EventLoop.cc 必须进链接，否则失败。

- 用 eventfd 当作被监控的描述符时，读回调若只置标志而不 read 掉计数，该描述符在后续阶段仍持续可读，WaitEvent 就会多返回本不该就绪的对象。迁移这类测试必须保留原有的 drain 步骤；本次迁移 TestEpoller 时漏掉 drain，Modify 段因此失败。

- 提高编译标准会激活只在更高标准下启用的警告，必须全量重建验证，不能只看改动点。`-std=c++11` 提到 c++17 后，自定义非 sized `operator delete` 触发 `-Wsized-deallocation`；补 sized 版本时必须转调非 sized 版本，若写成 `::operator delete[](p, size)` 会调用自身而无限递归。

- 看门狗不能用裸 `alarm`：SIGALRM 的默认动作直接终止进程，make 只留下 "Alarm clock"，无法定位是哪条断言挂住。应安装自定义处理器，内部只做异步信号安全的 `write` + `_exit`，并在每个用例开头重设预算。变异验证中"就绪事件永不产生"和"Update 空体"两项正是靠看门狗或异常逃逸暴露的——永久阻塞也是一种有效的失败模式，前提是它可被观测到。

- Channel 的监听位没有 public setter，一旦 Channel 改为经 EventLoop 转发，针对 Epoller 的测试就必须引入 EventLoop 才能让 Channel 带上监听位；但 EventLoop 的 `_ep` 私有，纯端到端驱动会丢掉 active 向量级别的断言。混合驱动（EventLoop 只提供监听位、裸 Epoller 承担登记与等待）能在迁移中同时保住两者。

- 头文件内联实现加互相包含会直接让整仓编译不过，且报错位置极具误导性：`TimerQueue.hpp` 包含 `EventLoop.hpp` 而后者回指前者，症状却是「`task_t` 未声明」「`read` 未声明」「EventLoop 类型不完整」。排查手段是对每个公开头文件单独做一次 `-fsyntax-only` 包含，以及单独编译每个 .cc；只看 `make` 的第一条报错会一路追错方向。判定「头文件是否自包含」只能靠这种方式，`make` 能过不代表头文件可用。

- 头/源分离的忠实度用机械比对而不是逐行人工核对：把拆分前后的文件各自做「去首尾空白 + 去空行」归一后取行集合求差，剩余差异应当全部能用「声明行、类名限定符、刻意改名、刻意修复」四类解释。这次正是靠它确认没有函数体被漏搬。

- 变异验证中出现「编译失败」不等于「已被捕获」：把 `return timeout > capacity ? capacity : timeout;` 改成 `return timeout;` 会让 `capacity` 变成未使用参数，被 `-Werror=unused-parameter` 拦下。这种时候必须换一种语义等价且不引入新警告的变异（如补 `(void)capacity;` 后保留原意），否则验证结论是假的。同类形态还有 `-Werror=unused-but-set-variable`：`MimeType` 只把 `return it == types.end() ? fallback : it->second;` 改成 `return extension;` 时，上一行的 `const auto it = types.find(extension);` 成了「已赋值未使用」而编译失败；此时要连那条查表语句一起删掉，才是对原始缺陷形态的忠实还原。判断标准是「能否编译通过」而不是「改动是否最小」。

- 断言应写成「这一步必须成功」，不要依赖自己推测的具体失败路径。`~TimerWheel` 不摘除登记时，预期的捕获是身份比较失败，实际是：析构释放的 fd 号被复用，新 Channel 由 `make_unique` 分配到与旧对象相同的地址，身份比较反而通过，最终由内核 `EPOLL_CTL_MOD` 返回 ENOENT 兜住。功能上没问题，但事后写文档若照搬推测就会失真。

- 边界归一化只做在入口：把 timeout 归一后存进 `TimerTask`，刷新路径用 `task->GetTimeout()` 重算时天然一致。若在每处用到 timeout 的地方各自钳位，添加与刷新就会走出两套边界。

- 给用户的修法建议在写进方案前必须先验一遍它是否成立，光"看起来显然"不够。这次提出的「把 `TimerTask*` 捕获进 lambda 做身份比对」，在 map 存 `weak_ptr` 的前提下就是错的：清理挂在 `~TimerTask` 上，此刻 `weak_ptr::lock()` 必然返回空（强引用计数已为 0），拿不到可比较的裸指针。`weak_ptr` 没有 `operator==`（它比的是被指对象地址、需要先 `lock()`），要判断「是不是同一个对象」应该用 `owner_before` 双向比较控制块。

- 改一个「删索引」的时机前，先问它是不是唯一的正确时机。把清理从 `~TimerTask` 挪到 `Tick()` 表面上更好写（任务还活着，`lock()` 可用），实际会破坏刷新语义：刷新过的任务同时挂在旧槽与新槽上，旧槽到期就摘索引，此后到新槽到期之间的整段时间里它既不能刷新也不能取消、却照样触发。析构才是「最后一根强引用消失」的唯一时刻，凡是靠对象生命周期收尾的清理都只能挂在那里。

- 「同一个 key 被新记录接管」时，旧记录的清理必须按身份而不是按 key 删除。索引类容器（id -> 引用）用「析构时按 id 删除自己」的写法时，旧对象一旦被新对象顶替，它的析构就会删掉新对象刚写下的记录，表现为新对象从此不能被刷新或取消、但照旧触发——静默且难查。这类断言要专门构造「旧对象先析构、再操作新对象」的时序才能覆盖。

- Connection 错误报告统一使用项目 LOG_ERROR，不另行使用 fprintf；在统一报告函数内部隔离日志异常，保证日志失败不跳过连接清理。

- 面向学习的收发结果处理，优先分开负数错误、零返回和正数字节数；仅在失败分支读取 errno，避免用合并条件掩盖不同语义。

- 解释所有权与生命周期问题时，先核实实际的持有关系再下结论，不能凭「谁指向谁」的直觉。`Connection` 持有的是 `EventLoop*` 裸指针（Connection.hpp 明确注释「不拥有它」），所以定时回调里捕获 `shared_ptr<Connection>` 的后果是**对象析构被推迟到时间轮槽位到期**（`TimerCancel` 只置 `_canceled`，任务对象仍留在槽里，最长 60 个 tick），而不是我先前所说的「引用环」。这类解释一旦说错，后续所有推理都会跟着错。

- `SwitchProtocol` 会整体替换四个业务回调（含关闭回调）。为它写用例时，若在调用它之前注册关闭回调，计数会永远是 0——切换把回调换成了空函数。涉及该接口的用例必须先切换、后注册需要观测的回调。

- 判定「某分支没有被覆盖」要以变异验证为准，不能靠通读代码下结论。本次候选里就有两条：`EnableInactiveReleaseInLoop` 的 `_release_pending || _released` 守卫删掉后，`HandleError` 的同名守卫会兜住，关闭通知仍只有一次；`HandleWrite` 的 `sent == 0`、`HandleEvent` 的 `TimerRefresh` 等也缺少可观测差异。这类用例写出来只会给出「测过了」的错觉。

- 断言必须落在**能区分变异**的观测点上。"析构时是否兜底注销登记"就无法用"对端收到 EOF / fd 已关闭"来证明——那些是 `~Socket` 的功劳，删掉 `_channel->Remove()` 后它们照样成立。可靠做法是制造同 fd 号重新登记的探针：`dup2` 把已释放的号码重新变成有效描述符，再登记新 Channel，残留表项会让这次登记失败（身份不符抛 `logic_error`，或地址恰好复用时由内核 `EPOLL_CTL_MOD` 返回 ENOENT 兜住）。断言写成「这一步必须成功」，而不是断言某种具体异常。

- 做变异归因实验（确认某条用例是不是某变异的唯一捕获者）时，直接把用例调用从 `main` 里删掉会触发 `-Werror=unused-function`，表现为编译失败——与「变异已被捕获」的结论混在一起就是假阴性。应改成保留引用而不调用，如 `(void)&CaseName;`。

- 用 `O_PATH` 描述符可以稳定构造 `fcntl` 的部分失败：`F_GETFL` 正常返回，`F_SETFL` 返回 EBADF。这为「非阻塞设置失败」提供了一条不需要伪造陈旧 fd、也不需要为测试目标新增 `--wrap=fcntl` 的干净路径。前提断言要写进用例，避免内核行为变化后静默失效。

- 改一个函数的参数类型时，必须回头检查原有的边界校验在新类型下是否仍然成立。`EnableInactiveRelease` 的参数从 `int` 改成 `uint32_t` 时，函数体里的 `if (timeout <= 0) throw ...` 一字未动，看起来仍然在防负数，实际已退化成只判 0：负数在实参转换处早就回绕成 4294967295，再被时间轮静默钳位到容量上限。规则：签名与校验条件是一对，改一边就要重新推导一遍另一边的语义，不能因为「代码没动」就默认它还有效。

- 没有接入任何构建目标的源码等于「不会报错的代码」。`Acceptor.cc` 曾有先 `Create()` 再 `CreateServer()` 导致绑定与监听被整体跳过的缺陷，还带着两个被丢弃的返回值，但因为它不在 Makefile 的任何目标里，从未参与编译——单独用项目同款严格参数做 `-fsyntax-only` 也是通过的，连 `-Werror` 都不会触发。规则：新模块写完立刻接一个编译目标，哪怕还没有测试。

- 调用一个「内部会再创建一次资源」的函数之前，必须先读它的实现。`Socket::CreateServer` 的第一句就是 `if (!Create()) return false;`，而 `Create()` 在描述符已存在时返回 false，所以先手动 `Create()` 再调 `CreateServer()` 会让后者在第一行就失败并跳过绑定与监听。两个函数名看起来是「分步」与「一步到位」的关系，实际是互斥的。规则：判断两个 API 能否串联，看被调方的实现，不看名字。

- 测试一个「绑定线程」的模块前，先确认它的线程归属契约落在哪一步。`TcpServer` 的 `EventLoop` 在构造函数里记录线程 id，`Acceptor::SetAcceptCallback` 又会校验当前线程，所以构造与 `Start()` 必须同线程；而 `Start()` 阻塞在主循环上，客户端的驱动逻辑只能放到另一个线程。动手写用例前没确认这一点，会先写出一版「在别的线程里 Start」的测试，然后在 `std::logic_error` 上白跑一轮。

- 析构函数里调用「会抛异常的注销接口」时，必须区分对象到底登记过没有。`Acceptor` 构造时只创建监听 Channel 不登记（登记在 `StartAccepting()`），而 `~Acceptor` 无条件 `Remove()`，于是「构造过但从未启动」的对象一析构就抛 `logic_error` 并 `terminate`。规则：析构路径上的清理动作，其前置状态要么由对象自己记录，要么接口本身对「本就没登记」幂等——`Connection` 用 `_registered` 记录，`Acceptor` 没记，差别就在这里。

- 断言「某操作被拒绝」时，若只捕获异常的基类，会接受「拒绝了，但拒绝得太晚」的实现。`std::system_error` 派生自 `std::runtime_error`，于是 `catch (const std::runtime_error &)` 同时接住了「在创建套接字处拒绝」和「带着无效描述符继续走到 epoll 登记才失败」两种情况，变异验证里这条用例因此假通过。修法是单独 `catch` 子类并把它判为失败。规则：断言异常类型等于断言语义，必须排除掉语义不同的子类。

- 把「一次调用 = 一轮」重新变成可独立调用的原语（`LoopOnce()`），比让每个测试自己造外层 `while` 更好。`Loop()` 改成持续循环后，六个测试目标挂在 `epoll_wait` 上，看起来是「测试写法过时」；真正干净的做法是把循环体抽成不循环的 `LoopOnce()`，`Loop()` 退化为 `while (!_quit) LoopOnce();`，测试改调单轮原语。规则：当循环语义变化时，先问「一轮」能不能是一个独立的、可被外部调用的操作，而不是急着改调用方。

- 一批测试长期挂在同一个位置时，它们后面的断言从未执行过，**不要把它们当作已验证**。`TestAcceptor.cc` 的 18 个用例全部按「构造即登记监听」写，而实现早已把登记挪到 `StartAccepting()`，头文件注释又是旧口径——三者不一致，但因为在改动前所有用例都卡在第一个 `Step()`，这个矛盾被完整地掩盖了。改完单轮驱动后，第一件事就是逐个跑一遍，而不是默认「原来就是绿的」。规则：解除挂死之后必须重新评估这批用例的断言是否还成立，这也是修 Loop 时必须连带处理的隐藏工作量。

- 变异验证结束后必须把源码还原并复查，残留的变异会伪装成「既有红项」。`TestBasic.cc:226` 留着上一轮的 `// MUTATION 4：对端关闭不回收`，导致 `check-integration` 从 2026-09-17 起一直红，而且被后来的几轮记成「与本轮改动无关的既有问题」，一路沿用。事后看，注释里明明写着 `MUTATION`，只要有人读一眼就能定性。规则：变异验证的副本要么放 `/tmp` 并在结束时删除，要么在还原后 `grep MUTATION` 复查；看到 `MUTATION` 字样的注释，先按「未还原」处理。

- 文档注释、实现、测试三者不一致时，先认定哪一个是「当前设计意图」再动手，不要默认注释或测试就是契约。`Acceptor` 的契约有三种可能的口径：注释说构造即登记、实现说 `StartAccepting()` 才登记、测试从不调用 `StartAccepting()`。判定依据不是谁的措辞更权威，而是**现有调用方怎么用**——`TcpServer::Start()` 先设 accept 回调再 `StartAccepting()`，说明「延迟登记」是刻意设计，于是改测试与注释，而不是改实现。

- 资源路径解析用于访问现有资源时，目标也必须存在；使用 canonical 并同步头文件契约和测试，不沿用允许目标缺失的 weakly_canonical 语义。收紧存在性要求后，越界测试要创建真实的站外目标，避免测试仅因不存在而失败，掩盖目录边界检查缺陷。

- 动手改代码前必须重新确认磁盘上的当前内容，不能沿用本会话早先的读取结果。本轮据会话开始时的 `Util.cc` 定下「修 3 处缺陷」的计划，实际那 3 处已在期间被改掉 2 处（文件时间戳比首次读取新），只有重读后才发现计划已经过期。IDE 里处于打开状态的文件尤其容易被并发编辑；判据是 `stat` 的时间戳与重新读取，而不是上下文里已有的那份内容。

- 检测「越界读 1 字节」这类缺陷，输入必须用**非空终止**的视图，否则测试会给出一条假绿。`UrlDecode` 的 `input.size() - i < 3` 少写一位后，`%4`、`a%4` 这类以 `const char*` 传入的输入会在越界处读到字符串字面量的 `'\0'`，`hex_value` 返回 -1，函数仍然正确地返回 false，缺陷完全不可见；只有 `std::string_view("A%4B", 3)` 这种视图外的字节仍是合法十六进制位时，越界才变成「返回 true 的错误结果」。同理，`std::string` 派生的视图在 `size()` 处也恒为 `'\0'`，用它同样测不出问题。

- 同一个 `CHECK` 行在循环里被反复执行时，失败信息只有行号，无法定位是哪个输入触发的。断言信息里必须带上数据：本轮把非法转义用例改为 `ExpectRejectedEscape(input)`，失败时打印 `accepted malformed escape: "%G0"`，才直接指出是哪个转义被误接受，而不是停在 `TestUrlDecode:338`。

- 以「词法/字符分类」实现的校验必须按标准收窄半开区间：`hex_value` 写成 `'a' <= ch <= 'z'` 会把 `%G0`、`%zz` 当成合法转义，`%G0` 解码出的是 NUL 字节、`%zz` 解码出的是 `'3'`，畸形请求被静默改写而不是拒绝。十六进制位只有 `0-9a-fA-F`；补测试时要同时钉住合法边界（`%AF`、`%af`、`%0a`），否则修复时容易把范围收得比标准更窄而无人发现。

- 「不包含 X」不是断言，是省略。`assert(wire.find("Content-Length") == std::string::npos)` 在实现把头块整个删空时照样成立，无法区分「正确省略该字段」与「什么都没生成」。凡是校验"某字段不该出现"的用例，都要同时精确比较整段报文或断言其余字段仍然齐全。

- 用状态码区间当断言等于放弃区分能力。`assert(status >= 400)` 会让 404 与 500 一视同仁，「内部错误」也能通过越界测试。断言要落在具体码上，除非该用例的目的本就是"只看成功与否"。

- 驱动被测函数的调用不能写在 `assert` 里。`assert(context.Parse(buffer) == Result::Complete)` 在定义 `NDEBUG` 的构建下整条语句被消除，测试变成空跑却仍然"通过"。要写成先取值再断言，这样无论哪种构建，副作用都发生。

- 事后采样证明不了「当次没有越界」。在 `Parse` 返回错误**之后**记录缓冲区内容，只能证明错误状态是粘滞的，无法证明那一次没有把数据吞掉。要证明"错误时不越界消费"，必须在调用**之前**记下期望值，然后比较调用之后的内容——本轮专门为此写了一条用例，因为其它任何写法都测不出这个契约。

- 校验必须发生在状态改动之前。`SetHeader` 是"先删全部同名项再追加"，如果把入参校验放在追加处，一次被拒绝的调用就已经把调用方原有的字段删干净了。规则：凡是会抛异常的 setter，校验一律写在函数最前面，让失败调用对对象**零影响**，并把这条写进断言。

- 修「同一信息有两个来源」时，跳过条件要收窄到真正产生冲突的场景。`Serialize` 需要跳过调用方设置的 `Location`，但只有在**发生重定向**时才该跳；无条件跳会让「手工设 Location 而不重定向」这个合法用法直接丢失该字段。收窄条件比扩大跳过面更安全，代价是条件里多一个标志位。

- 私有成员「没被使用」本身不是问题，危险在于它躲过了一致性清理。`HttpRequest::_matches` 全仓零引用，看着只是冗余；但 `Reset()` 清空了全部其它成员却独独漏掉它，一旦将来有人写入匹配结果，`Reset` 就会留下指向已释放字符串的迭代器。删死成员的理由是"它不在任何不变量里"，不是"它现在没用"。

- 变异被既有断言抢先捕获时，不能就此宣称新用例有价值。M8、M10 首轮都死在早就存在的断言上，新增用例是否真有检测力完全未知。做法是做归因实验：把抢先捕获的那条断言一并移除，再看新增用例能否独立失败。**「新增用例能独立捕获」才是证据**，「变异被捕获了」不是。

- 要证明某条断言不是空转，唯一可靠的手段是构造一个**只改变被观测的那一件事**的变异。想让新的字段校验去接住"版本被记错"的变异就失败了——版本同时参与 Host 校验，变异在更早的分支就被拦下。最后是把"星号目标被存成什么"单独改掉（不触碰任何解析逻辑），才真正隔离出 `GetPath()` 断言，并以"还原旧脚手架后变异存活"反证了它的检测力。

- **读「某个线程」的 CPU 必须走 `/proc/<pid>/task/<tid>/stat`**。直接读 `/proc/<tid>/stat` 拿到的是**整个进程**的 utime+stime：本轮实测四个线程各报 1.05s，而进程总共只有 1.05s。这个错法很隐蔽——「各线程 CPU 之和是进程总量的 4 倍」看起来像个合理的巧合（4 个线程嘛），差一点就据此写出「负载不均」的结论。判断读数是否可信的办法是**交叉校验**：各线程之和应当等于进程总量，不等就是采样坏了，结论全部作废。

- **共享机器上做基准，噪声本身就是要报告的结果，不是可以忽略的干扰**。本机基线负载 1.85（云监控代理、IDE、语言服务等），同配置重复运行出现双峰：慢轮里服务端多烧 40%～60% CPU 却做同样的活。对策是三条一起上——每配置重复多次取**中位数**、同时报**区间**、关键结论用**多组独立测量交叉印证**；并且**绝不引用单次数字**。另外要区分两种噪声来源：客户端与服务端互相抢占（靠绑核隔离）、以及机器上的其它负载（无法隔离，只能多次测量）。

- **绑核要按场景分配，不能一刀切**。多线程服务端需要多核，客户端也需要 CPU：给服务端 3 核 + 客户端 1 核适合吞吐场景（客户端只占 0.2～0.4 核），但延迟场景客户端要 0.7～1.2 核，就得改成服务端 2 核 + 客户端 2 核。而**短连接场景客户端要 1.3～1.7 核**，一开始给了 1 核，结果客户端先饱和、测出来「多线程反而更慢」的假结论。**每次调整场景都要重新确认客户端没有成为瓶颈**（看它占了多少核、有没有顶到自己分到的上限）。

- 「读代码看起来该优化」和「实测能优化」之间有很大差距：本轮三项最像热点的改动全部不成立。`HandleRead` 每次读事件 `memset` 64 KiB 看着像明显浪费（约 6 µs/次），实测去掉后是 0.95×～0.99×，落在噪声内；给服务端加 `TCP_NODELAY` 看着该显著降延迟，实测 +4% / 0.98×；「发送时先直接写、写不完再进缓冲」看着能同时省一次拷贝和两次 `epoll_ctl`，实测在流水线下只剩 **0.02×**。规则：性能结论必须落到实测数字上，读代码只能用来**提出**假设，不能用来**下结论**。

- 一个优化在一种负载下有效、在另一种下可能是灾难，**必须跨负载验证**。直接写在 depth=1（一问一答）是 +26%，在 depth=32（流水线）是 −98%，p50 恰好是 32 × 40 ms 的延迟确认。原因要追到底：基线那份"看起来低效"的缓冲写其实在做**写合并**——实测每 32 个响应才 1 次 `sendto`，这正是它的长处；改成逐响应直接写就退化成 32 次小写，被 Nagle 与延迟确认互锁。**优化之前先量出被改掉的那部分到底在做什么**，否则会把优点当缺点改掉。

- 性能对比必须带上机制证据，否则只是两组数字。本轮「事件位幂等化」的结论不只靠吞吐 +21%～27%，更有 `strace -c` 的直接计数：depth=32 时 `epoll_ctl` 从 15,864 降到 984（16 倍）、系统调用总数从 17,033 降到 2,146（8 倍），而 depth=1 完全不变——**这个「只在批量时才变」的形状恰好是机制预言的样子**，比单一吞吐数字有说服力得多。

- 同机跑基准时，"谁的瓶颈"必须先量出来再解释结果。本轮一开始看到吞吐封顶而服务端只占 1.00 核中的一部分，很容易误判成"CPU 没跑满所以不是 CPU 瓶颈"；实际是我用**外层脚本的墙钟**去除 CPU 时间，而那个墙钟含进程启动与预热，系统性偏低。改用测量内部的墙钟后，服务端恰好是 0.98～1.00 核，结论完全反转成"就是单核跑满"。同理，多线程组一开始把服务端绑到单个核上，3 个 worker 与主循环抢同一个核，并行度被人为抹掉——**绑核要求两侧都吃得开时才用，否则它自己就成了瓶颈**。

- 基线里"低效"的写法可能有隐藏价值，动手前先量化它。`Connection::SendInLoop` 无条件把响应拷进输出缓冲再开写事件，看着多了一次拷贝和两次 `epoll_ctl`；但同一份实测数据显示它把一批响应合并成一次 `send`。把这两件事分开看——**拷贝与注册抖动是要改的，合并是要留的**——才能得出正确改法（幂等化事件位）而不是错误改法（改成逐响应直接写）。

- 信号处置会跨越 `exec` 传给子进程，**被忽略的信号在 `exec` 之后仍然是忽略的**。端到端测试为了自保把 `SIGPIPE` 置 `SIG_IGN`，`fork` + `execv` 之后被测程序继承的就是 `SIG_IGN`——于是它自己有没有写那行 `signal(SIGPIPE, SIG_IGN)` 完全看不出来，针对该行的变异必然存活。要测进程的真实行为，子进程 `execv` 前必须把被测方会设置的信号显式恢复成 `SIG_DFL`，否则测的是父进程的选择而不是被测对象的。

- 断言失败会 `abort`，**RAII 析构不会执行**，凡是"启动子进程"的测试都会在失败时泄漏子进程。本轮变异验证实测泄漏 30 多个占着端口的孤儿服务器，而且因为它们是失败路径的产物，很容易被当成"环境里本来就有别的东西"而忽略。做法是子进程里 `prctl(PR_SET_PDEATHSIG, SIGKILL)`，让内核在父进程消失时直接清理；注意 `fork` 与 `prctl` 之间有个窗口，父进程若恰好在此退出，`PDEATHSIG` 不会再触发，所以紧接着要核对一次 `getppid()`。

- 端到端用例的断言必须能区分"真的跑到了"和"空转"，而证明方式是**测试侧变异**：把期望值改错，用例必须失败。本轮把并发用例的 `failures == 0` 翻成 `> 0`、把探针期望的 200 改成 500、把启动参数的期望退出码改成 2——四条全部失败，才敢说这些断言是活的。前几轮做的是"生产者侧变异"（改实现看测试是否报警），方向互补，缺一不可。

- **变异存活不一定是测试的问题，也可能是那条代码本来就不可达**，但必须查清是哪种，不能停在"存活"两个字上。本轮三处 SIGPIPE 防护的变异全部存活，逐层追下去才落实：RST 用例确实走到了写路径（用"写路径错误分支抛异常"的变异证明被捕获），服务端日志里是三行 `Failed to send: errno=104`；104 是 ECONNRESET，而 Linux 上只有 EPIPE 才附带 SIGPIPE；`HandleWrite` 的错误分支立刻置位 `_release_pending`，函数开头的守卫让后续写回调直接返回，不会有第二次写，EPIPE 于是永不出现。结论是这两处防护在当前结构下不可达——这比"测试没测到"是更准确也更可用的结论，因为它同时说明了"将来什么改动会让它变成可达"。

- 同一判据被多个模块各自实现时，**只有在它开始承重之后，重复才从「冗余」升级为「缺陷」**。RFC 9110 的 token 字符集在 `HttpContext`、`HttpServer`、`HttpResponse` 里各有一份，长期相安无事；直到响应侧拿它做字段名校验，两侧就变成了「客户端能发送的字段名」与「服务器能写回的字段名」必须一致的一对约束，而没有任何东西保证这两份定义不漂移。判断一处重复该不该合并，问的不是"像不像重复"，而是"有没有一个必须同时成立的不变量横跨它们"。合并之后，证明"真的合并了"的唯一方式是逐个调用点分别做变异——把共享实现改坏，三个调用点要各自失败，否则可能只是删掉了拷贝、留下了一条没被删干净的分支。

- 修完一个"该输出而没输出"的字段后，紧接着要问"哪些状态码**禁止**输出这个字段"。`Content-Length` 就是这样：205 缺它是个 bug（keep-alive 上客户端会等一个永不到来的正文），而 1xx 与 204 加上它同样是个 bug（RFC 9110 §8.6 明确禁止）。正确做法不是把「禁止正文」与「是否输出该字段」继续合成一个判据，而是拆开——204 是"不出正文、也不出长度"，205 是"不出正文、但必须出长度为 0"。

- 跨调用累计的额度检查，测试数据必须落在「剩余额度」与「总额度」之间才测得出来。只发一条超长行时，两种实现（按已用字节扣减 / 永远用总额度）都会报同一个错；要在先消费掉一段头部之后，再送入一段长度介于二者之间的无换行数据，才能把"忽略已用额度"的实现区分出来。实测用 1000 字节已用头部 + 32000 字节无 CRLF 数据，恰好卡在 31768 与 32768 之间。

- **一块自带整圈描边的独立色块，压在另一个物体上面，就一定读成"摆在上面的东西"，跟它的外轮廓画成什么形状无关。** 本轮改握把姿势，前五轮都在调包握轮廓的形状（圆蛋→柳叶→扁平片），每一版都还是像"搁在车把上的鹅卵石"或"小饺子"。真正的分水岭是发现它是一块独立 path，有自己完整的一圈描边，又整块落在棕色握把上——于是无论怎么改轮廓，它都被那圈描边框成一个独立物体。解法不是继续修形状，而是让包握的两端伸到握把之外、落在翅膀上，从翅膀的方向收成细尖接进去，使它看起来是从翅膀长出来的一片，而不是贴上去的一块。**判断"像不像一体"要看两个形状是否共享边界，不看各自画得像不像。**

- **`getCTM()` 给的是到「元素像素」的矩阵，不是到 viewBox 坐标系的。** 本轮用它把 viewBox 坐标换算到元素局部坐标，结果 `isPointInStroke` 全部返回 false、扫描出 0 段握把，而断言的报错是"应该有 2 段实际 0 段"，看起来像几何画错了。实测矩阵的 a=1.0783（= 容器宽 1294 / viewBox 宽 1200）才反应过来缩放被算进去了。**跨坐标系做点变换时，先把两个坐标系之间的那个缩放找出来并显式换算**，否则错的是坐标系而不是被测对象。

- **`getPointAtLength` 采样后取 argmax，在轮廓接近竖直的地方是不可用的。** 想测"翼尖随身体起伏是否漂移"，取全局 x 最大的采样点再看它的 y，报出 7.94px 的漂移，是起伏幅度 1.6px 的 5 倍——看着像个真 bug。原因是该处曲线几乎竖直，x 对参数几乎不敏感，离散采样落点在竖直方向能差好几像素。改成取 x 落在最大值附近 0.5px 内那一小段点的 **x、y 均值**，漂移立刻变成 0.059px。**argmax 只能用来定位"在哪"，不能用它的另一个坐标当测量值**；要测就得在平台段内取均值。

- **新增的断言必须用变异证明它不是空转，这次连静态属性也要纳入。** 本轮新增"静态 `d` 必须等于 JS 模板串在 bob=0 时的展开"，因为首页刚被外部格式化工具重排过，这种"两处描述同一件事"的地方最容易在别人改格式时偷偷漂开。构造变异时只动了静态 `d` 里的一个数字、完全不碰 JS 模板串，断言如期失败，随后逐字节还原并核对 md5。**改动一个静态文件前先备份到 `/tmp` 并留一份 md5**，本轮 `Http/www/` 整个目录未纳入版本控制，没有这道保险就不敢做变异实验。

- **形状类改动不要停在"上一个版本更好看"，要能把判据落到数字上。** 这一处前后渲染了十版，每版都"看起来不太对"但说不清哪里不对。真正收敛是从把观感拆成三个可测量的量开始的：握把两端露出的长度（沿车把中心线逐像素判定）、包握的高宽比、拱顶高出握把上缘多少。基线量出来是"露出合计约 7px、高宽比 0.68、拱顶高出约 10px"，改完是"17px、0.56、4.85px"，进展立刻变得可比较、可回归。**先测基线再动手，"像不像"才有讨论的基础。**

- **"看不见"不等于"没画"，要先把遮挡关系算出来再下结论。** 车把看起来浮在车架上方，第一反应是"少画了连接件"。实测把立从 (666,300) 出发后向**左上**折到 (657,268) 再绕回车把，而这段左上折正好落进翅膀的覆盖区（翅膀在 x=657 处占 y∈[258,272]，把立在 x=657 处是 y=268）—— 连接件一直在，只是升上去的那截被挡住了，露出来的部分朝左上方消失，眼睛就接不上右边的车把。**定位这类问题要把每个元素的覆盖区间算出来逐点判遮挡**，我用的是"沿路径密采样 + `isPointInFill`/`isPointInStroke` 剔除被盖住的点，再看剩余可见段的最上点在哪"。

- **判断"某个东西没在动"，要先问它动起来看不看得出来。** 齿盘确实不转（它画在不参与动画的分组里），但就算把它放进旋转组也还是看不出 —— 它是个没有任何细节的正圆，转与不转在视觉上完全一样。所以"让齿盘转起来"这件事的真正内容是"给齿盘补上非旋转对称的细节"（盘爪与盘钉），旋转只是顺带。**同样地，加"三者必须同步"这类断言时必须同时断言"被同步的那个量确实在变"**，否则三者都静止也会通过；我用的是 48 次采样里要求取到 ≥40 个不同角度。

- **两根肢体从侧面看重叠时，靠"同形缩小 + 偏移"读出数量，靠"偏移量"控制可读性。** 补远侧那只手时前两版都失败：第一版做成一个大圆球，盖住了握把右端，把上一轮验收过的"露出握把两端"直接破坏；第二版做小了但仍是一块独立的圆片，读成"车把上搁了个东西"。最终做法是把近侧包握的轮廓整体缩放 0.78、向右上平移 (+7,−5)，因为它俩形状完全相同，露出来的那道弧自然读成"后面还有一只手"。**代价是偏移量同时决定两件事**：偏移越大越读得出是两只手，越小越容易被当成同一只手的描边重影；这次的可接受区间是靠"握把两端仍各露出 ≥5px"这条既有断言框住的。

- **把一条 path 拆成两条，是让"连接关系"变得可断言的前提。** 把立与车把原本是一条 path，于是没法问"把立的可见段朝向哪里"。拆成 `#handlebar-stem` 与 `#handlebar` 之后才写得出"沿把立中心线剔除被遮挡的点，取可见段最上点，断言其 x 落在头管顶 ±4 内"这条断言 —— 而且它在旧代码上会判失败（实测最上点在 x=658.48，偏了 7.52），可以直接当作修复前后对照。**遇到"某个东西连接得不对"这类描述，先想办法把它拆成可单独测量的部件，再谈怎么改。**

- **"某个数字能不能整除另一个数字"这类断言，是本轮唯一能直接编码缺陷的断言。** 雨幕横向跳动的原因就是位移 20 不是平铺宽度 70 的整数倍；这条判据一旦写成断言（从 `@keyframes` 解析平移量、从 `<pattern>` 解析宽高、断言两者整除），它就不只是"这次修好了"，而是"以后谁再改这两个数都会被拦下"。雪天有同一个缺陷（130 宽对 −30），是靠把这条断言推广到三个图层才发现的 —— **写完一条判据要立刻问"还有谁符合这个形状"**。

- **动画的方向不能靠符号推，要量。** `stroke-dashoffset` 递减到底是让链节朝路径起点还是终点走，光看代码推很容易反。做法是把动画停掉、手动设三个值（0、−半周期、−一个周期）各截一张图，量同一段路径上首个亮链节的像素位置：0 → 495.17，−8.5 → 505.83（前移），−17 → 495.17（回原位）。**这一条同时验证了两件事** —— 方向对，且周期确实整除（走过一个周期后渲染应完全重合）。**凡是有"正负号/顺逆时针"歧义的动画，都要留一条会实际位移的断言**，否则改反了没人发现。

- **平铺图案的位移必须落在平铺格上，否则循环处必然跳。** `patternUnits="userSpaceOnUse"` 下图案随元素坐标系一起平移，动画复位时图案相对画面就跳了一个"位移量 mod 单元尺寸"。这条对雨、雪、任何滚动纹理都成立，只要位移的两个分量分别是单元宽高的整数倍就严丝合缝。**排查这类"看着像在抖"的问题，先算位移与平铺格的关系，比盯着动画曲线看有效得多。**

- **Playwright 的 `page.clock` 不驱动 CSS 动画。** 装上模拟时钟后 `getComputedStyle(el).strokeDashoffset` 恒为 0，而同样的代码去掉装表就能读到 -20.57 这样递减的值 —— CSS 动画由合成器自己的时间轴驱动，不吃 `Date`／`rAF` 的 mock。**用 `clock.install()` 的脚本里不要在断言 CSS 动画**；反过来，靠 `elapsed` 累加驱动的 JS 动画（本项目里骑行动画就是这样）才该用模拟时钟，因为它需要可重放的确定性。

- **像素级验证里，截图坐标系与页面坐标系差一个默认 margin。** 用 `page.setContent('<svg ...>')` 做最小复现时，`<body>` 默认有 8px margin，于是我按 SVG 坐标去读截图像素时整体错位，扫出来的"墨迹"是一整条横杠，看着像 dasharray 没生效。**要么显式 `body{margin:0}`，要么直接对目标元素 `locator.screenshot()` 取得"元素自身坐标系"的图**，后者更稳 —— 本轮最终能测出方向就是换成了元素截图。

- 用户要求保持性能并简化 Logger 时，优先合并辅助状态、集中刷新流程，不凭代码行数替换热路径；用同环境交替基准复核，候选改动出现一致下降时保留原热路径实现。

- 「这个函数调用在热路径上，改它要小心」必须先看代码生成再下结论。等级转换的双向 switch 曾经因为「怕动热路径」被保守保留，还撤回过一版查表实现（交替对照下降 4%–9%）。本轮把 `-O2` 对象反汇编出来看，GCC 早已把两个 switch 分别编译成「范围判断 + 身份转换」和「跳转表」，`ShouldLog` 里更是折成一条 `cmp $0x5; jbe`。改成「取值直接对齐 spdlog 枚举 + 一次范围校验后的 cast」后，归一化比对 37 行指令逐字节相同。**查表之所以慢，是它引入了热路径上的依赖加载，cast 没有；把「用 switch 还是用表」当成同一类选择是错的。** 规则：热路径的保守决策要有反汇编或基准作依据，不要因为「看着像热路径」而保留冗余代码。

- 第三方库提供的回调式钩子，看起来是「等价替换掉自己那层 RAII」，实际可能重新引入该 RAII 专门消除的窗口。spdlog v1.12 的 `thread_pool` 支持 `on_thread_start`，用它替换 `BlockWorkerSignals` 能少 17 行；但回调运行在库线程内、`pthread_create` 之后，此时线程已可被调度，中间那段「掩码还没屏蔽」的窗口正是要在创建前屏蔽、让新线程继承才能消除的。**判断依据是「新线程第一次可被调度时状态对不对」，不是「最终状态对不对」——** 现有用例只断言最终掩码，替换后照样全绿，这个退化在测试里是隐形的。改动这类「时序保证」的代码前，先问测试断言的是最终状态还是发生时序。

- `pthread_join` 返回**不代表**内核已摘除 `/proc/self/task` 条目：唤醒 join 的 `clear_child_tid` 在 `exit_mm` 阶段写入，条目清除在随后的 `release_task`。最小实验（创建线程、join、立即 `opendir/readdir` 计数）在**空载**下 20000 次里出现 136 次残留，约 0.7%；重负载下窗口变宽，于是只在并行 `make check` 里偶发失败、单独重跑 15 次全过。**「单独跑能过、集成跑偶发失败」不要先归因于环境噪声，先把探测手法本身证伪。** 修法是只在线程「消失」方向上等待并设上限（真泄漏的线程不会自行消失，仍会被断言抓住），不要改成「重试到通过」——那会让真缺陷也通过。
