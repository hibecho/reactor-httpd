# 性能测试报告

测量对象是 `main.cc` 构建出的真实服务器进程（`make -C Http` 产出的 `.build/HttpServer`），
客户端是新增的基准工具 `Http/Test/BenchHttpServer.cc`：`fork`/`exec` 启动被测二进制，
每连接一个客户端线程、阻塞式 keep-alive、逐次用 `steady_clock` 记延迟。

**本轮只测量，没有改动任何生产代码。** 所有 A/B 实验都在 `/tmp` 的源码副本上编译成独立二进制，
与基线对照。

## 一、环境与方法

| 项 | 值 |
| --- | --- |
| CPU | Intel Xeon Platinum 8255C @ 2.50GHz × 4 |
| 内存 | 3.6 GiB |
| 内核 | 6.8.0-124-generic |
| 编译器 | g++ 13.3.0（`-std=c++17 -Wall -Wextra -Werror -pedantic -UNDEBUG`） |
| glibc | 2.39 |
| `perf_event_paranoid` | 4（**perf 不可用**，见「未覆盖范围」） |

方法上的几处刻意安排，都是为了数字可信：

- **客户端自己设 `TCP_NODELAY`**。否则 Nagle 会出现在客户端一侧，服务端有没有设就成了测不出的变量。
- **绑核**。默认把服务端绑到核 0、客户端绑到其余核；多线程服务端的实验会让两边都吃 CPU，
  这时绑核反而制造瓶颈，因此那几组用 `BENCH_SERVER_CPUS=off` 关掉绑核。
- **每轮重启服务器**，避免长时间运行累积状态影响后一轮。
- **每组重复 3 次取中位数**，原始每一轮的数字都在工具输出里。
- **报出客户端 CPU**。同机测试里客户端先饱和是最容易犯的错，每张表都带这一列供核对。
- **延迟按「每请求」折算**。流水线深度 > 1 时一轮含多个请求，表中数字是轮耗时除以深度。

一条必须先说的局限：**服务端与客户端跑在同一台 4 核机器上**。两者争抢 CPU，
因此下文的绝对吞吐数字应看作「这台机器上能到多少」，而不是该实现的固有上限。

### 2.3 载荷维度（`POST /echo`，conns=4，单线程）

| 0（`GET /`） | 25,525 | — | 37.5 | 4.8 MB |
| 4 KB | 24,498 | 191.4 | 40.0 | 4.5 MB |
| 64 KB | 9,753 | 1,219.1 | 100.0 | 5.6 MB |

- 8 MB 时效率略降（1.55 µs/KB），与缓存容量有关。
- 峰值 RSS 随载荷线性上升：2 × 8 MB 并发时 63.5 MB，即**每个在途的大响应都完整驻留多份**。

## 三、瓶颈分析（每条都挂到证据）

### F1 单线程事件循环是吞吐的硬上限 —— 数据支持

`main.cc` 固定 `SetThreadCount(0)`。证据：并发扫描里服务端占用**从 4 连接起就恒为 1.00 核**，
再往上加连接只增加排队延迟不增加吞吐；depth=32 时同样是 1.00 核封顶 15 万 req/s。
E3（把工作线程池打开）在同一配置下把吞吐提到 2.46×～3.04×。

### F2 写事件注册被逐响应重设，浪费掉大部分系统调用 —— 数据支持

`Channel::EnableWrite()`/`DisableWrite()` 无条件调用 `Update()` → `EventLoop::UpdateEvent` → `epoll_ctl`，
**不检查事件位是否真的变化**（`src/Channel.cc:34-50`）。而 `Connection::SendInLoop` 每个响应都要
`EnableWrite()` 一次、排空后再 `DisableWrite()` 一次（`src/Connection.cc:218-231`、`279-284`）。

证据链：depth=1 时 `epoll_ctl` 恰好 2.01 次/请求，与「一开一关」完全对应；
depth=32 时是 15,864 次 / 15,360 请求 ≈ 1.03 次/请求，即批内每个响应各来一次。
把事件位幂等化后，depth=32 的 `epoll_ctl` 从 15,864 降到 **984（16 倍）**，
系统调用总数从 17,033 降到 **2,146（8 倍）**，吞吐 +21%～27%，depth=1 无变化（那里事件位确实每次都变）。

### F3 一问一答场景的绝大部分 CPU 花在唤醒开销上 —— 数据支持

2.2 节：占用恒为 1 核，每请求 CPU 随深度从 37.8 µs 降到 5.8 µs。差额约 32 µs 与「每次请求一次
`epoll_wait` 唤醒 + 事件分发 + 缓冲与分配」对应。这解释了单连接只有 12.7k req/s。

### F4 大载荷按约 1 µs/KB 计价，且随载荷线性占内存 —— 数据支持

2.3 节。拷贝链路是 `recv`→输入缓冲→正文串→`Serialize` 拼整串→输出缓冲→`send`，
每字节至少走两到三遍；8 MB 并发两路时峰值 RSS 63.5 MB。

### F5 直接写：**不采纳** —— 数据不支持（且有害）

我原本的假设是「先尝试直接写、只在写不完时进缓冲」能同时省掉一次拷贝和两次 `epoll_ctl`。
实测在 depth=1 确实 +26%，**但在流水线下是灾难：depth=32 只剩基线的 0.02×，p50 恰好 1281 µs
≈ 32 × 40 ms 的延迟确认**。

原因已定位：基线的缓冲路径会把一整批响应合并成**一次** `send`（2.5 节：32 个响应 1 次 `sendto`），
改成逐响应直接写就变成 32 次小写，被 Nagle 与延迟确认互锁住；即使补上 `TCP_NODELAY`
也只恢复到 0.29×，因为 32 次独立系统调用的 CPU 成本本身就是基线（每 32 响应 1 次）的三倍多
（CPU/请求 6.5 → 22.8 µs）。

**结论：写合并是这套实现的优点，必须保留。** 这一项的价值在于排除了一条看起来显然的优化路径。

### F6 TCP_NODELAY：收益无法证实 —— 数据不支持

单独加在服务端：depth=1 时 +4%（在轮间波动内）、depth=32 时 0.98×。
解释与 F5 同源：基线的写合并让 Nagle 根本没有可扣的数据，所以没有延迟可省。
它只在「已经采用逐响应直接写」时才变成必需（把 0.02× 救回 0.29×）。**建议不单独引入。**

### F7 去掉 64 KiB `memset`：无可测量的收益 —— 数据不支持

`Connection::HandleRead` 每次读事件都 `memset(buffer, 0, 65536)`（`src/Connection.cc:158-159`），
读代码时看像明显的浪费（约 6 µs/次）。实测去掉后 depth=1 是 0.95×、depth=32 是 0.99×，
**都在噪声范围内，甚至略负**。原因可能是该缓冲常驻 L1/L2、清零与随后的 `recv` 系统调用有重叠。
**不建议为它单独改动**——收益无法证实，而改动本身要承担回归风险。

### F8 资源占用随并发与载荷线性增长 —— 数据支持

2.1 与 2.3 节。无泄漏迹象（三次重复的峰值 RSS 稳定），但也没有上限控制：
256 连接 30.6 MB、2 路 8 MB 回显 63.5 MB。生产部署需要按并发上限估算内存。

## 四、优化方案

按「预期收益 × 实现代价 × 风险」排序。所有收益都是**这台 4 核机器上实测**的相对值。

### P0 把写事件注册改成幂等（已实测，建议优先做）

- **做法**：`Channel::EnableWrite` / `DisableWrite` / `EnableRead` / `DisableRead` 在事件位已经是目标
  状态时直接返回，不调用 `Update()`。约 10 行。
- **实测收益**：流水线下 **+21%～27%** 吞吐、p50 −18%～22%、系统调用减少 8 倍；depth=1 无变化（无损）。
- **代价与风险**：低。语义不变——只在「事件位没变」时跳过内核调用，而那种情况下 `epoll_ctl` 本就是空操作。
  需要留意的是 `Update()` 另有「未登记就抛错」的副作用，只在已登记通道上调用这几个函数才安全
  （现有调用点都满足）。**必须确认**这一前提在改动后仍成立。
- **验收指标**：`depth=32`、`conns=16` 的吞吐相对基线 ≥ +20%，`strace -c` 的 `epoll_ctl` 降到
  每批次 1 次量级；同时跑全量 `check` 与 `check-sanitize` 证明没有行为回归。

### P1 让工作线程池真正参与（已实测，收益最大）

- **做法**：`main.cc` 把 `SetThreadCount(0)` 改为按核数设置（如 `nproc - 1`）。这不是代码缺陷，
  而是示例程序当初为了简单刻意固定成单线程。
- **实测收益**：`conns=16/depth=32` 从 15.3 万到 **46.4 万 req/s（3.04×）**；depth=1 也有 1.71×。
- **代价与风险**：中。需要确认多线程下的共享状态：`HttpServer` 的 `_routes` 与 `_document_root`
  在 `Start()` 后只读 ✓；`TcpServer` 的连接表按既有约定只在主循环线程读写 ✓；
  但**这一条必须在实施时用测试证伪，而不是默认成立**——它同时牵涉 `LoopThreadPool` 的线程创建与回收。
- **验收指标**：多线程配置下 E2E 与全量测试全绿；吞吐 ≥ 2×；`/proc/<pid>/fd` 与峰值 RSS 不随
  连接数单调增长。

### P2 直接写 —— **明确不采纳**

见 F5。它在延迟敏感场景的 +26% 会被流水线场景 −70%～−98% 完全淹没，而流水线是 HTTP/1.1
客户端的常规行为。

### P3 TCP_NODELAY —— 不单独采纳

见 F6。除非将来重新考虑 P2，否则没有证据支持引入。

### P4 去掉 `memset` —— 不采纳

见 F7。保持现状。

### P5 降低一问一答的唤醒开销 —— **未测量，需要先做剖析**

F3 指出 depth=1 时约 85% 的 CPU 在唤醒开销上，但**具体构成没有测量**：本轮 `perf` 不可用
（`perf_event_paranoid=4`），所以拿不到热点函数分布。可以继续排查的方向（均为假设，未经验证）：
`RunInLoop` 的 `std::function` 与 `shared_ptr` 分配、`Serialize` 拼整串的多次 `+=`、
每请求的若干次 `std::string` 分配、以及每个事件都做的 `TimerRefresh`。
**在拿到剖析数据之前，不建议对这些动手**——F5/F6/F7 三项已经说明「读代码看起来该优化」的地方
未必真能优化。

## 五、未覆盖范围

- **没有热点函数剖析**。`perf` 在本机不可用（`perf_event_paranoid=4`，禁止 CPU 事件访问），
  本轮以 `strace -c` 的系统调用构成与 `/proc` 的 CPU/内存计数作为替代。P5 因此停在假设阶段。
- **同机测量**。客户端与服务端争抢同一台 4 核机器，绝对吞吐不宜外推；多线程组的客户端
  一度成为限制（客户端占用 0.87～0.91 核时，服务端只能到 2.6 核），所以 3.04× 是**下界**。
- **只测了回环**。真实网络的 RTT、丢包、带宽限制、Nagle 与延迟确认在跨机场景下的表现都不同，
  尤其 F5/F6 的结论依赖回环的低延迟特性。
- **没有长时间稳定性与内存增长测试**。每轮只有几秒到几十秒，没有覆盖小时级的连接反复建立/断开。
- **没有测 HTTPS、没有测静态文件**（`main.cc` 未配置站点目录），大响应路径只覆盖 `POST /echo` 回显。
- **没有测空闲超时的开销**。`main.cc` 开了 `EnableInactiveRelease(30)`，时间轮每 tick 1 秒，
  端到端跑不动；`Connection::HandleEvent` 在每个事件上都会 `TimerRefresh`，这部分成本未单独测量。
- **没有测工作线程数的最优取值**。只试了 3 个 worker。
- **基础库未单独测量**。`Buffer` 的精确扩容（`std::vector::resize` 精确尺寸 + 清零）在读代码时
  像热点，但没有单独的实验把它与其它因素分开。

## 六、复现方式

```bash
cd Http
make -C . .build/BenchHttpServer 2>/dev/null || \
  g++ -Iinclude -std=c++17 -Wall -Wextra -Werror -pedantic -o .build/BenchHttpServer Test/BenchHttpServer.cc -pthread
make                                  # 构建被测的 .build/HttpServer

# 用法: <binary> <connections> <rounds> <depth> <payload> <repeat>
./.build/BenchHttpServer ./.build/HttpServer 16 500 32 0 3        # 吞吐敏感
./.build/BenchHttpServer ./.build/HttpServer 4 10000 1 0 3        # 延迟敏感
./.build/BenchHttpServer ./.build/HttpServer 2 16 1 8388608 3     # 8 MiB 回显

# 多线程服务端的实验要关掉绑核，否则 3 个 worker 会与主循环抢同一个核
BENCH_SERVER_CPUS=off ./.build/BenchHttpServer <多线程二进制> 16 500 32 0 3
```

输出每条 `RUN` 是单轮结果，`MEDIAN` 是三轮中位数；`server_cpu_s / wall_s` 就是服务端占用几个核。
